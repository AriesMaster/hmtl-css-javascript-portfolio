01 / Project Overview

Building a Role-Based Dental Platform

BrightSmile Dental is an ongoing portfolio project. Its goal is to bring patient, dentist and administrator workflows together in one application.

01 — ADMIN

Practice Administration

Administrative users manage the dental service catalogue through protected CRUD endpoints.

  • Create and update services
  • Delete eligible services
  • Enforce service validation
  • Prevent duplicate service names
02 — PATIENT

Patient Experience

Patients can authenticate, retrieve their identity, maintain profile information and view dental services.

  • JWT-based login
  • Personal profile endpoints
  • Browse available services
  • Appointment booking planned
03 — DENTIST

Dentist Workflow

The Dentist role is part of the application's access model. Appointment-related workflows are planned for the next development phase.

  • Role-specific access model
  • Assigned appointment viewing planned
  • Appointment status updates planned
  • Scheduling management planned

02 / System Design

Application Architecture

The application separates frontend presentation, backend request handling and relational data persistence.

Angular SPA Components, routes, forms and HTTP requests
→
ASP.NET Core API Controllers, DTOs, validation and JWT
→
PostgreSQL Supabase with Entity Framework Core

Angular communicates with the API over HTTP. Entity Framework Core handles database access through Npgsql.

Backend Organization

Controller-based API with dedicated request and response DTOs, EF Core entities, application services and a database context.

  • Controllers handle HTTP operations
  • DTOs define API contracts
  • Models represent database entities
  • ApplicationDbContext manages persistence
  • JWT and email services provide supporting functionality

Database Design

Relational entities support account management, personal profiles, service catalogues and the future appointment workflow.

  • Users with unique email addresses
  • One-to-one User and Profile relationship
  • Services with decimal prices
  • Appointments referencing patients, dentists and services
  • EF Core migrations for schema evolution

03 / Security

Authentication & Authorization

The backend uses JWT bearer authentication and role-based authorization to protect sensitive operations.

JWT Authentication

After successful login, the API issues a token containing user identity and role claims. Protected endpoints validate the bearer token.

Role-Based Access Control

The backend restricts service modification endpoints to administrators. A Patient token cannot bypass these authorization rules.

04 / Backend Engineering

RESTful Dental Services API

The service catalogue supports CRUD operations, request validation, duplicate prevention and role-based access restrictions.

Method Endpoint Purpose Access
GET /api/Services List dental services Public
GET /api/Services/{id} Retrieve service details Public
POST /api/Services Create a service Admin
PUT /api/Services/{id} Update a service Admin
DELETE /api/Services/{id} Delete a service Admin

DTO Validation

Request DTOs enforce constraints on service names, descriptions and prices. Invalid requests are rejected with meaningful validation errors.

Business Rules

Duplicate names are rejected with HTTP 409 Conflict. The delete operation also checks whether existing appointments reference the service.

07 / Problem Solving

Challenges & Lessons Learned

Transient Database Failure

An Npgsql connection interruption occurred during an update test. Retrying the request succeeded, highlighting the importance of distinguishing infrastructure failures from application logic defects.

Authentication vs Authorization

A valid Patient JWT allowed identity retrieval but not administrative service creation. This demonstrated the difference between proving identity and granting permissions.

Meaningful HTTP Responses

The API uses HTTP 400 for invalid data, 403 for forbidden operations, 409 for duplicate conflicts and 204 for successful deletion.

API Documentation

Swagger showed some valid error responses as "Undocumented". This identified an opportunity to improve OpenAPI response metadata.
