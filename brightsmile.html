BrightSmile Dental

A role-based dental practice management system developed using Angular, ASP.NET Core 10 Web API and PostgreSQL. The backend implements secure authentication, appointment scheduling, conflict prevention, service management and role-specific workflows.

01 / Project Overview

Building a Role-Based Dental Platform

BrightSmile Dental is a full-stack portfolio application designed around three user roles: Administrator, Dentist and Patient. Its backend supports the core dental appointment lifecycle, while the Angular dashboards are being developed to expose these capabilities through a complete user interface.

01 — ADMIN

Practice Administration

Administrative users manage the dental service catalogue and have access to appointment administration endpoints.

  • Create dental services
  • Update service information and pricing
  • Delete eligible services
  • View all appointments
  • Manage authorized appointment statuses
02 — PATIENT

Patient Experience

Patients can authenticate, manage their profiles and interact with appointment booking endpoints.

  • Register and sign in
  • View available dental services
  • Book dental appointments
  • View personal appointment history
  • Reschedule pending appointments
  • Cancel eligible appointments
03 — DENTIST

Dentist Workflow

Dentists have protected endpoints for retrieving assigned appointments and managing appointment statuses.

  • Authenticate using the Dentist role
  • View assigned appointments
  • Confirm pending appointments
  • Complete eligible appointments
  • Follow controlled status transitions

02 / System Design

Application Architecture

The application separates frontend presentation, backend business logic and relational database persistence.

Angular SPA Components, routing, forms and HTTP communication
→
ASP.NET Core 10 API Controllers, DTOs, JWT, validation and business rules
→
PostgreSQL Supabase, EF Core and Npgsql

The Angular frontend is hosted on Netlify. The ASP.NET Core backend is hosted on Render, with Supabase providing the PostgreSQL database. Entity Framework Core handles relational persistence through Npgsql.

Backend Organization

A controller-based Web API organized around HTTP endpoints, request and response DTOs, entity models, application services and EF Core.

  • RESTful API controllers
  • Request and response DTOs
  • Entity Framework Core
  • Dependency injection
  • JWT authentication services
  • Role-based authorization

Database Design

Relational entities support account management, patient profiles, service catalogues and appointment scheduling.

  • Users with unique email addresses
  • User and Profile relationship
  • Dental services with decimal prices
  • Appointments linked to patients and dentists
  • EF Core migrations

03 / Security

Authentication & Authorization

Authentication establishes user identity, while server-side role and ownership checks determine which operations are permitted.

JWT Authentication

After successful login, the backend issues a JSON Web Token containing identity and role claims. Protected endpoints validate the bearer token before processing requests.

Role-Based Access Control

Admin, Dentist and Patient roles have different permissions. Additional ownership checks prevent patients from modifying another patient's appointments and restrict dentists to their assigned bookings.

05 / Appointment Management

Appointment Scheduling & Lifecycle

Appointment management introduces business rules beyond basic CRUD, including scheduling conflicts, ownership checks and controlled status transitions.

Appointment Booking

Patients can book appointments with a selected dentist and dental service. The backend checks whether the requested time overlaps with an existing active appointment.

  • Future appointment date validation
  • Dentist and service validation
  • 30-minute appointment windows
  • Overlapping booking prevention
  • Adjacent time slot support

Rescheduling & Cancellation

Patients can reschedule their own pending appointments and cancel eligible bookings. Cancelled appointments release their reserved time slots.

  • Patient ownership verification
  • Conflict checks during rescheduling
  • Cancellation workflow
  • Rebooking cancelled time slots
  • HTTP 409 responses for conflicts

Appointment Status Management

Authorized dentists and administrators can update appointment statuses according to defined business rules.

  • Pending to Confirmed
  • Confirmed to Completed
  • Eligible appointments to Cancelled
  • Invalid status transitions rejected

Database Transaction Handling

Scheduling mutations use PostgreSQL transactions and dentist-specific advisory locks to coordinate appointment changes. This is designed to reduce the risk of simultaneous conflicting bookings.

Dedicated concurrent-request testing is still planned.

Scheduling Conflict Test

With an existing 09:00 appointment, a booking request at 09:15 was rejected with HTTP 409. A booking at 09:30 was accepted with HTTP 201, demonstrating the intended 30-minute slot boundary behavior.

Cancellation & Rebooking Test

Appointment cancellation returned HTTP 200 and changed its status to Cancelled. A new booking for the same time subsequently returned HTTP 201.

08 / Problem Solving

Engineering Challenges & Lessons

Preventing Double Bookings

Comparing appointment timestamps for exact equality was insufficient because partially overlapping appointment windows could still be accepted. The scheduling logic was improved to detect overlapping 30-minute appointment intervals.

Authentication vs Authorization

A valid JWT proves user identity but does not grant unrestricted access. Role checks and appointment ownership validation protect sensitive operations.

Database Reliability

A transient PostgreSQL connection failure occurred during local testing. Retrying succeeded, highlighting the importance of distinguishing infrastructure issues from application logic defects.

API Documentation

Swagger exposed valid HTTP responses that were not fully documented in the OpenAPI response metadata. Improving response annotations remains a future refinement.
