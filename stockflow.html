Full-Stack Software Engineering Case Study · In Development

StockFlow

StockFlow helps a small hardware store prepare supplier orders. Staff maintain supplier catalogues, compare prices on order lines and save drafts in rand.

Two suppliers can sell the same box of screws at different prices. StockFlow ties each offer to a supplier and saves the agreed price when a buyer creates an order.

Project Overview

From Supplier Catalogue to Draft Purchase Order

The current implementation covers supplier and product setup, supplier-specific offers, and creating and viewing draft orders. Partial receiving and inventory updates are planned for a later stage.

Purchase Orders

A purchase order belongs to one supplier and can contain several product lines. Draft creation, listing and details are implemented; approval is planned.

Goods Receiving

Receiving is the next workflow stage. The database and domain design describe partial deliveries, but the REST endpoint and screen are not implemented yet.

Inventory Tracking

Inventory balances and stock movements are planned. The current application does not update on-hand stock when an order is created.

System Users

Four Roles, One Procurement Workflow

StockFlow is an internal employee system supporting multiple accounts per role. Administrators provision employee accounts; public registration is not available.

Administrator

Manage employee accounts, suppliers, products and catalogue prices. Administrators can also create and review draft orders.

Purchasing Officer

Select a supplier, add items at its agreed prices and save a draft purchase order.

Approver

Review order details. Approval and cancellation actions are planned.

Warehouse Officer

View the items and quantities on an order. Recording deliveries and updating stock are planned.

Every active role can read suppliers, products, offers and orders. Spring Security checks permissions on each request.

System Architecture

Angular, Spring Boot and PostgreSQL

Angular provides the protected workspace. Spring Boot hosts authentication, administration, catalogue and draft purchase-order APIs. PostgreSQL stores current records plus the schema reserved for future receipt and inventory processing.

Angular Frontend

The Angular workspace connects the employee, supplier, product and order screens to the API. A buyer can search one supplier’s offers, adjust quantities and open the saved draft from the order directory.

Java Domain Model

The model handles order state transitions and quantity validation. Typed exceptions and problem-detail mapping are in place for business-rule failures.

Relational Model

Flyway V1–V6 define the business, authentication, supplier, product and supplier-catalogue schema. JPA mappings support users, products, suppliers, supplier offers and purchase orders. Receipt/inventory application services and transactions remain future work.

Purchase Order Workflow · Current Progress

One Supplier, Multiple Product Lines

A purchase order is a store's request to buy products from one supplier. It can contain several products, but each item must be offered by the selected supplier at that supplier's price.

1. Select the Supplier

The form searches active suppliers. When the user chooses one, StockFlow loads only that supplier's active product catalogue. Changing supplier clears the current draft lines.

2. Add Products and Quantities

For example, adding 20 boxes of screws at R12.50 per box gives a line total of R250.00. The buyer can add other products offered by the same supplier.

3. Save and Review the Draft

The API validates the supplier and offers, then stores the product name and unit-price snapshots. The order directory supports status filtering and detail views.

Approval, cancellation and delivery receiving are not implemented yet. The planned receiving example is 12 of 20 units delivered, leaving 8 outstanding; inventory will only change once receipt processing is built.

Engineering Decisions

Security by Design

Employees sign in through Spring Security. The API uses the employee’s current role and session when it authorizes a catalogue change or a new purchase order.

Spring Security & Argon2id

Database-backed credential verification uses salted Argon2id hashes rather than plaintext or reversible encryption. Four roles model administration, purchasing, approval and warehouse responsibilities.

JWT & Session Lifecycle

Signed 15-minute access tokens, seven-day sessions and SHA-256 refresh-token digests. Transactional rotation uses a pessimistic session lock and revokes a session on detected reuse. PostgreSQL concurrency tests verify refresh rotation and replay handling.

Angular Security Boundary

Signals keep access tokens in memory. The interceptor restricts token attachment to API paths; guards control navigation. The backend enforces employee, supplier, product and catalogue roles. All active roles can read orders; ADMIN and PURCHASING_OFFICER can create them. Approval and warehouse receipt authorization awaits those endpoints.
